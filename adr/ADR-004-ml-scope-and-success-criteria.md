# ADR-004: Объём ML-конвейера и критерии успеха K1–K6

**Статус: принят**, с одним открытым выбором формулировки (K6, см. ниже — одна из двух версий уже закрыта). Предыдущая версия этого
документа ссылалась на задачи `A4`, `Doc6`, `M17` как на источник критериев K2/K3 —
этих идентификаторов не существует ни в одном репозитории проекта (проверено прямым
поиском по всем шести репозиториям); эти ссылки были ошибочной выдумкой при первой
редакции ADR, не реальным бэклогом. Таблица ниже заменяет их проверяемыми ссылками на
код и README, которые эти критерии реально закрывают.

## Контекст

Диплом защищается на конкретном, измеримом результате, а не на «система умеет
обнаруживать атаки» без чисел. Нужен явный, заранее согласованный список классов атак,
которые лаборатория воспроизводит и модели учатся отличать от фона, и список критериев
успеха, по которым эксперимент в главе 4 считается пройденным или нет.

## Решение

### Классы атак (воспроизводятся `deploy/lab`, размечены в `labeled_flows`/`labeled_dns`)

Floods (`syn_flood`, `udp_flood`, `icmp_flood`), сканирование (`port_scan`,
`slow_scan`, административный `nmap` как доброкачественный трудный негатив), туннели и
скрытые каналы (`dns_tunnel` — эмуляция и реальный `iodine`, `c2_beacon`), `slowloris`,
доброкачественные профили с высокой нагрузкой или высокой DNS-энтропией
(`benign`/hard-negative: потоковое видео, `iperf3`, SSH, резервное копирование, легитимный
трафик CDN/DKIM/SPF). Полный и актуальный список — `deploy/lab/campaigns/v1.yaml`, он
меняется чаще, чем этот документ, и в этом ADR не дублируется построчно.

### Критерии успеха K1–K6

| # | Критерий | Статус | Где реально закрыт |
| --- | --- | --- | --- |
| K1 | Точность обнаружения по классам атак (precision/recall/F1, ложные срабатывания) | **сделано** | `ml/README.md`, разделы «Baseline: …» и «Фреймворк оценки (M8)»: `evaluate_baseline_by_scenario` считает precision/recall/F1/FPR по каждому сценарию для всех четырёх baseline'ов; `evaluate compare` добавляет PR-кривые, `average_precision` и тест Макнемара |
| K2 | Задержка «пакет → алерт» (p50, p95) | **сделано** | `ml-online-detector` (M16): `detect run` печатает `latency_ms p50/p95` по всем детекциям при завершении (`netstream_ml.detector.run_kafka_detector`); честно документирована и отрицательная задержка при принудительном `flush()` |
| K3 | Накладные расходы агента (CPU, память, `bpf_stats`) | **сделано** | `agent` экспортирует `netstream_agent_memory_rss_bytes`, `netstream_bpf_run_time_ns_total`, `netstream_flow_active` и др. (`agent/src/bpf/overhead.rs`, `agent/src/bpf/maps.rs`) через OTLP; `deploy` пишет их в ClickHouse (`agent_metrics`, миграция `012_agent_metrics.sql`) и строит дашборд Grafana «NetStream / Sensor health» |
| K4 | Устойчивость к перемене условий | **сделано** | Три разных эксперимента в `ml/README.md`: чувствительность к интенсивности атаки (M9), перенос на внешний датасет CIC-IDS2017/CIC-DDoS2019 (M10), смещение между эмуляцией и реальным инструментом `dns_tunnel`/`iodine_tunnel` (M11) |
| K5 | Воспроизводимость: весь стек и весь эксперимент поднимаются одной командой | **сделано** | `deploy`: `just up` (основной стек), `just lab-up` + `just lab-campaign` (лаборатория с реальными атаками и манифестом кампании) |
| K6 | Не определено — два кандидата; один из них закрыт с момента предыдущей редакции этого ADR, второй не начат | **открыт** (выбор формулировки), но один из двух кандидатов уже **сделано** | см. ниже |

**K6, подробно.** Два кандидата на формулировку:

- *Полнота набора baseline-сравнений.* **Сделано.** `evaluate compare` (M8) теперь сравнивает все четыре baseline'а — пороговые правила, Isolation Forest, Random Forest и Gradient Boosting (PR-кривые, разброс по сидам, все шесть попарных тестов Макнемара). Gradient Boosting (M7) был добавлен после M8 и не входил в сравнение — это и было единственным незакрытым пунктом этой формулировки, устранено отдельным изменением `ml`.
- *Соответствие требованиям приватности (152-ФЗ).* Проверено прямым поиском по всем репозиториям («privacy», «персональные данные», «152-ФЗ», «анонимиз…») — ни кода, ни документации на эту тему нет вообще, 0% готовности.

Если K6 имелась в виду как «полнота сравнения baseline'ов» — критерий закрыт, можно цитировать по номеру. Если как «приватность» — работа не начата. Какая из двух формулировок верна (или третья) — решение автора бэклога, у этого документа нет полномочий угадывать дальше.

## Последствия

K1–K5 можно цитировать в главе 4 диплома по номеру уже сейчас, со ссылками на код/README из таблицы выше. K6 цитировать можно только после выбора формулировки: если это «полнота сравнения», ссылка готова (`ml/README.md`, раздел «Фреймворк оценки (M8)», обновлённый `evaluate_compare_w<N>.json` с четырьмя моделями); если «приватность» — эта работа ещё не начата.

## Отвергнутые варианты

- **Не фиксировать критерии успеха вовсе, оценивать «на глаз» по метрикам, которые
  окажутся под рукой к моменту защиты.** Отвергнуто: K1 (`evaluate compare`), K2
  (`detect run`'s p50/p95) и K3 (`agent_metrics`/Sensor health) уже существуют именно
  как код и дашборды, производящие числа под конкретные критерии, — значит критерии
  нужно зафиксировать текстом, привязанным к этому коду, а не восстанавливать по коду
  постфактум для каждой новой главы диплома отдельно.
