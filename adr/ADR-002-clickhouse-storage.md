# ADR-002: ClickHouse как телеметрийное хранилище

## Контекст

Data plane генерирует поток сетевых событий с кардинальностью, растущей с числом
сенсоров и объёмом трафика: сырые потоки, DNS-запросы, срабатывания блок-листа,
агрегаты по времени. Хранилище должно быстро принимать записи вставками, отдавать
диапазонные и агрегатные запросы (дашборды, обучение моделей) и не деградировать при
росте объёма на порядки.

Первой реализацией backend была TimescaleDB (см. историю репозитория `backend`,
коммиты `feat(database): add timescale db integration` и последующий
`chore(backend): remove dead gRPC/proto/Timescale stack`) — она была полностью удалена
вместе со связанным с ней gRPC-приёмом, не доведена до продакшена рядом с текущим
стеком.

## Решение

Телеметрия (потоки, DNS-запросы, срабатывания блок-листа, агрегаты, метрики агента)
хранится в ClickHouse (`deploy/clickhouse`). Схема — сырые OTLP-таблицы (`otel_logs`,
`otel_metrics_*`) с коротким TTL и материализованные представления поверх них,
превращающие сырые записи в типизированные таблицы с более долгим хранением: `flows`,
`dns_queries`, `blocklist_hits`, минутные агрегаты `flows_1m`, метрики агента
`agent_metrics`.

## Последствия

- ClickHouse хранит только телеметрию с высокой кардинальностью и append-only
  характером записи; состояние control plane (пользователи, сенсоры, конфигурация,
  реестр моделей, инциденты) — отдельно, в PostgreSQL (см. `docs/architecture/system.md`,
  раздел «Целевая архитектура», и миграции `backend/internal/storage/postgres`). Смешивать
  их в одной СУБД означало бы либо мириться с MergeTree для точечных транзакционных
  апдейтов, либо тащить в Postgres миллионы строк телеметрии — оба варианта хуже
  разделения.
- Материализованные представления и раздельные TTL позволяют независимо настраивать
  срок хранения сырых записей (короткий, только для отладки конвейера) и производных
  таблиц (для дашбордов и обучения — длиннее).
- Grafana и `ml` подключаются read-only учётной записью (`deploy` migration
  `013_read_only_role.sql`) — ни дашборд, ни аналитический запрос не может повредить
  данные, даже ошибочно.

## Отвергнутые варианты

- **TimescaleDB** — была первой реализацией, полностью удалена вместе с тогдашним
  gRPC-приёмом. Причина отказа не задокументирована на момент удаления; повторно не
  рассматривалась при выборе текущей схемы, поскольку ClickHouse уже показал приемлемую
  производительность на кампаниях лаборатории без отдельного тюнинга.
- **Prometheus** для событийной телеметрии (потоки, DNS) — годится для агрегатных
  метрик (и действительно используется на уровне метрик самого агента до попадания в
  Kafka/ClickHouse), но не предназначен для хранения и последующего произвольного
  агрегатного анализа сырых событий с атрибутами высокой кардинальности (IP, домен) —
  для этого нужна колоночная СУБД, а не time-series база метрик.
