# ADR-005: Модель реагирования — allowlist, monitor-only по умолчанию, TTL, лимиты карт

## Контекст

Автоматическое реагирование на сетевом сенсоре рискованно по конструкции: ошибочное
правило может заблокировать легитимный трафик или, в режиме `gateway`, поставить в
карантин сам сенсор или его единственный путь наружу. Нужна модель, которая по
умолчанию безопасна, обратима и явно управляема, а не «включить блокировку и
надеяться».

## Решение

- **Monitor-only по умолчанию** (`RESPONSE_MODE=monitor`, см. ADR-001) — новый сенсор
  ничего не блокирует, пока это не включено явно.
- **Allowlist, не выключаемый оператором в режиме `gateway`**: локальные адреса машины,
  DNS-резолверы из `/etc/resolv.conf`, шлюз по умолчанию — вычисляются и вставляются
  автоматически при каждом запуске (`agent/src/response.rs`, `ResponseConfig::from_settings`),
  плюс дополнительные адреса из `QUARANTINE_ALLOWLIST`. Сенсор не может заблокировать
  сам себя или единственный путь к сети, даже ошибочной конфигурацией.
- **TTL, а не постоянный бан**: карантин (`QUARANTINE_TTL_SECS`, по умолчанию 60 секунд)
  снимается автоматически по истечении времени — ошибочное срабатывание самовосстанавливается
  без вмешательства оператора.
- **Ограниченные по размеру eBPF-карты, а не неограниченный рост состояния**:
  `blocked_ips` (карантин) — LRU-хэш на 4096 записей, `quarantine_allowlist` — LPM_TRIE
  на 256 записей. При переполнении вытесняются наименее недавно использованные записи
  (LRU), а не падает вставка новой — стабильность важнее полноты списка при аномальном
  всплеске числа уникальных источников.
- **Горячее обновление без потери счётчиков**: и блок-лист доменов
  (`RELOAD_POLL_MS`/`SIGHUP`), и allowlist, приходящий из control plane (десиред-конфиг
  сенсора, `backend`), обновляются добавлением/удалением только изменившихся записей в
  уже загруженной eBPF-карте — без перезагрузки программы и без обнуления счётчиков
  срабатываний.

## Последствия

- Оператор может включить `gateway` на новой машине без риска потерять к ней доступ —
  это снижает порог для активного реагирования на площадках, где раньше стоял только
  `monitor`.
- Подпись блок-листа (Ed25519) и проверка версии при получении от control plane —
  **пока не реализовано** (см. бэклог агента, задача A7). Сейчас содержимое, которое
  агент подтягивает из control plane, ничем криптографически не защищено от подмены на
  пути от backend до агента — это открытый риск, который стоит закрыть до того, как
  control plane станет обязательным элементом развёртывания, а не опциональным.
- Режим `dry-run` для команд control plane (получить и залогировать решение, не
  применяя) для карантина ещё не существует — существующий allowlist-hot-apply уже
  логирует полный payload при каждой новой версии конфига независимо от того, что из
  него применилось, что даёт частичную видимость уже сегодня.

## Отвергнутые варианты

- **Постоянный бан без TTL** — отклонено: превращает любое ложное срабатывание в
  постоянную проблему, требующую ручного вмешательства, вместо самовосстановления.
- **Allowlist, полностью заменяемый удалённой конфигурацией** (без обязательных
  локальных адресов/резолверов/шлюза) — отклонено: единственная ошибка в
  конфигурации control plane не должна быть способна отрезать сенсор от сети или от
  собственного DNS.
